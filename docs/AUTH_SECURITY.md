# Защита авторизации: правила и эксплуатация

Состояние: итерация 3, 2026-11-09. Реализация — services/auth_limits.py. Пароли остаются scrypt с прежними salt/параметрами; cookie-сессии и reset-токены сохраняют существующий контракт.

## Аудит маршрутов

| Маршрут | Доступ | До итерации | После итерации |
| --- | --- | --- | --- |
| POST /api/auth/register | Публичный | Нет квоты, 409 выдаёт наличие email | Квота IP/email; мгновенная регистрация и 409 сохранены по решению владельца |
| POST /api/auth/login | Публичный | Нет квоты, каждый запрос выполняет scrypt | IP + IP/email до хеширования; общая квота аккаунта включает проверку запроса |
| POST /api/auth/logout | Сессия/AuthUser | Удаляет текущую сессию | Без изменения: выход и действующие сессии не блокируются квотой входа |
| POST /api/auth/password | Сессия/AuthUser + текущий пароль | Нет квоты попыток текущего пароля | IP + user_id; отзыв старых сессий/reset-токенов сохранён |
| POST /api/auth/forgot-password | Публичный; нужен SMTP | 10/IP/час, 3/email/час; отсутствует Retry-After; read/insert/update | Те же начальные пороги, атомарные квоты, Retry-After |
| POST /api/auth/reset-password | Публичный; нужен действительный одноразовый токен | 20/IP/час без Retry-After | Тот же порог; лимит проверяется до изменения пароля |
| GET /api/auth/me | Сессия | Срок сессии и существование пользователя | Без изменения |
| /api/builds, изменение профиля, создание/удаление лотов | Сессия + owner checks | Проверка владельца и Origin на изменяющих AuthUser-запросах | Без изменения |

Пароли: hashlib.scrypt(n=16384,r=8,p=1), индивидуальный salt, compare_digest. Несуществующий аккаунт выполняет тот же password hash по фиктивному salt. Сессии: случайный токен 32 байта, в БД SHA256, HttpOnly/SameSite=Lax, Secure по COOKIE_SECURE; срок 30 дней или один день, проверяемый сервером. Reset-токен: случайный 32-байтный token_urlsafe, SHA256 в БД, 30 минут, DELETE RETURNING для одноразового использования. SMTP-ошибка логируется без токена и удаляет недоставленный reset-токен.

## Начальные пороги

Все значения читаются Settings из переменных окружения; примеры добавлены в backend/.env.example и .env.amvera.example.

| Настройка | По умолчанию | Причина |
| --- | --- | --- |
| AUTH_LOGIN_WINDOW_SECONDS | 900 | Временное окно 15 минут |
| AUTH_LOGIN_IP_LIMIT | 60 | Ограничение распыления по разным аккаунтам и дорогих scrypt-запросов |
| AUTH_LOGIN_PAIR_LIMIT | 10 | Допускает несколько опечаток; сдерживает один IP/email |
| AUTH_LOGIN_ACCOUNT_LIMIT | 20 | После распределённых попыток для одного email требуется дополнительная работа клиента |
| AUTH_REGISTER_WINDOW_SECONDS | 3600 | Часовое окно регистрации |
| AUTH_REGISTER_IP_LIMIT / ACCOUNT_LIMIT | 5 / 3 | Массовые аккаунты и повторные попытки одной регистрации |
| AUTH_PASSWORD_WINDOW_SECONDS | 3600 | Часовое окно смены пароля |
| AUTH_PASSWORD_IP_LIMIT / ACCOUNT_LIMIT | 20 / 10 | Ограничение ошибок текущего пароля; user_id доступен только после авторизации |
| AUTH_RECOVERY_WINDOW_SECONDS | 3600 | Сохранён прежний часовой срок |
| AUTH_RECOVERY_IP_LIMIT / ACCOUNT_LIMIT | 10 / 3 | Сохранены прежние квоты SMTP-запросов |
| AUTH_RESET_IP_LIMIT | 20 | Сохранён прежний порог проверок reset-токена |
| AUTH_CHALLENGE_BITS | 18 | Работа клиента сверх общей квоты аккаунта; не проверка знания пароля |
| AUTH_CHALLENGE_TTL_SECONDS | 120 | Короткий срок одноразового разрешения |
| AUTH_IPV6_PREFIX | 64 | Адреса одной IPv6 /64 делят IP-квоту; препятствует простой ротации privacy-адресов |

Считаются поступившие валидные запросы, включая успешные. Успешный вход не обнуляет IP-квоту. Блокированные запросы не продлевают начало окна. Ровно на границе окна квота восстанавливается. Для HTTP 429 Retry-After содержит положительное число секунд; Cache-Control=no-store. При невозможности записать квоту SQLite возвращается 503/Retry-After=1, запрос не пропускается без контроля.

Тело неверного логина одинаково для известного и неизвестного email. Проверка аккаунтной квоты выполняется до поиска User. Ключ нормализуется тем же strip/lower, что и Credentials. Счётчики сохраняют SHA256 ключа, а не пароль/исходный email/IP.

## Распределённые попытки без жёсткой блокировки по email

Простой запрет всех входов после N обращений к email даёт постороннему способ заблокировать владельца. Поэтому общая квота аккаунта является порогом усиления проверки, а не флагом блокировки пользователя.

После 20 обычных допусков за 15 минут API возвращает HTTP 429 с detail.message и detail.challenge (token, bits, expires_in). Это одинаково для существующего и несуществующего аккаунта. Браузер перебирает nonce, чтобы SHA256(token + ":" + nonce) начинался с bits нулевых битов, и повторяет вход с challenge_token/challenge_nonce.

- Токен случаен (256 бит); в новой auth_challenges хранится его SHA256, привязка к нормализованному аккаунту/IP, сложность и срок.
- Привязка к IP использует ту же IPv6-группу, что и квота.
- DELETE RETURNING атомарно поглощает разрешение; один ответ не допускает два параллельных запроса и не работает для другого IP/email.
- После общей квоты каждый следующий допуск требует отдельной работы клиента. Неправильное решение тоже поглощает совпавший токен.
- Жёсткие квоты IP/IP-email действуют и при правильном решении.
- Существующая сессия остаётся действительной при атаке. Правильный новый вход с другого IP проходит с проверкой, что подтверждено тестом.
- Клиент делает не более одного автоматического повтора. Расчёт ограничен 45 секундами; ошибка оставляет понятное сообщение ожидания.
- В production нужен HTTPS/WebCrypto; localhost подходит для разработки. API-клиентам при такой нагрузке нужно реализовать тот же ответ либо дождаться Retry-After.
- Это повышение стоимости распределённого перебора, а не гарантия против ботнета/GPU или общего DDoS. При масштабных атаках нужна защита на сетевом периметре; хеширование паролей этим механизмом не заменяется.

## SQLite, конкуренция и очистка

Для счётчиков переиспользуется reset_request_limits. Admission выполняется SQLite INSERT ON CONFLICT UPDATE ... WHERE ... RETURNING; проверка максимума и увеличение являются одним атомарным действием. Транзакции короткие и заканчиваются до scrypt/SMTP. Тест 20 конкурентных обращений допускает ровно 10 по паре IP/email; тест одноразового разрешения допускает ровно один из двух параллельных повторов.

AuthChallenge — новая аддитивная таблица, создаваемая обычным Base.metadata.create_all при запуске. Нужен перезапуск backend; существующие users/sessions/builds/listings и reset-счётчики не удаляются.

Истёкшие разрешения и счётчики старше максимального настроенного окна удаляются при новых запросах к защищённым маршрутам. Во время простоя записи могут оставаться на диске; при следующем обращении очистка возобновляется, сами ограничения истекают независимо от фоновой задачи.

Разные соединения/процессы с одним локальным SQLite-файлом видят общие счётчики (проверено через второй engine). При отдельных файлах разных реплик глобальных квот нет. SQLite на сетевом общем диске не следует считать решением горизонтального масштабирования. Для UpgradeLab по-прежнему рекомендована одна реплика из-за существующей очереди поиска. При высокой конкурентной записи возможен 503; Redis в этой итерации не добавлялся.

## Reverse proxy и Amvera

Приложение использует только request.client, нормализует IPv4/IPv4-mapped IPv6 и группирует IPv6 по настроенному префиксу. Непригодный адрес попадает в общий bucket unknown. X-Forwarded-For и X-Real-IP приложение самостоятельно не читает.

[Uvicorn: proxy headers и forwarded-allow-ips](https://uvicorn.dev/settings/#http) описывает доверие к непосредственным прокси через FORWARDED_ALLOW_IPS/--forwarded-allow-ips. Переменная должна быть в окружении процесса до запуска Uvicorn, а не только в .env, который позже читает Pydantic. Wildcard "*" означает доверие всем и не подходит.

Проверены исходники установленного Uvicorn 0.34 и локальные моки: заголовки от недоверенного peer игнорируются; для доверенного peer выбирается последний недоверенный hop справа, а не подставленный пользователем левый IP.

Адреса/CIDR ingress Amvera и гарантия перезаписи/добавления заголовков в доступной конфигурации и найденной документации не подтверждены. Они не придуманы и не внесены в конфиг. Перед публичным запуском:
1. Подтвердить у хостинга непосредственные proxy IP/CIDR и правила цепочки X-Forwarded-For.
2. Установить узкий FORWARDED_ALLOW_IPS в реальном окружении запуска.
3. Проверить с двух внешних клиентов, что backend различает адреса, а подставленный заголовок не меняет квоту.
4. Сохранить COOKIE_SECURE=true и HTTPS.
5. Не задавать "*" или все частные сети наугад.

Без этой настройки backend может видеть общий IP ingress: защита останется консервативной, но пользователи будут делить квоту. Production-конфигурация Amvera в этой итерации не проверялась.

## Ограничения и осознанные решения

- По подтверждённому выбору владельца регистрация сохраняет мгновенный вход и 409 для существующего email. Возможность проверки email через регистрацию остаётся, хотя её частота ограничена. Полное устранение требует другого контракта регистрации/подтверждения email; утверждать, что перечисление аккаунтов полностью устранено, нельзя.
- Отказ SMTP и ограничение рассылки не блокируют существующий пароль/сессию. Злоумышленник может занять квоту отправки на один email; уже выданная ссылка остаётся действительной до использования/истечения.
- NAT/общая IPv6-сеть делят квоту. Фиксированные окна допускают всплеск на стыке периодов; начальные пороги следует уточнять по реальной нагрузке.
- Это прикладные квоты валидных auth-запросов. Они не заменяют лимит HTTP body, соединений и malformed-запросов на сервере/периметре.
- Проверки Origin у login/register, подтверждение владения email и отдельная DNS-защита сетевых импортов не изменялись.

## SSRF: только аудит этой итерации

POST /api/offers/from-url требует AuthUser; OfferLink ограничивает HTTPS, домен и товарный путь известной площадки. Анонимный импорт и произвольный loopback URL проверены без сети: 401/422, fetch не вызван. Публичные /offers/search и search-jobs могут запрашивать только существующие источники/поисковые сценарии; прямого поля произвольного импортируемого URL в них нет.

Остался ранее описанный P1-риск DNS/браузерных подзапросов (UL-007). Критический обход и обращение к внутреннему ресурсу не продемонстрированы; утверждать наличие такого блокера по факту открытого импорта нельзя. Реальные внутренние адреса не запрашивались. Исправление SSRF не начато.
