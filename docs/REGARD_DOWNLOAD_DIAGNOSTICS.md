# Диагностика и исправление скачивания XLSX Регарда

Проверка выполнена 10.11.2026 UTC (ночь 10/11 ноября по Asia/Krasnoyarsk), локально на Windows. **Официальный XLSX действительно скачан готовым Python-загрузчиком и импортирован в отдельную SQLite.** Рабочая БД, .env, Hardware пользователя, биржа и сохранённые сборки не изменялись. Commit/push/deployment не выполнялись.

## 1. Что подтверждено о HTTP 403

Старый минимальный запрос SafeSession к `https://www.regard.ru/api/site/pricelist` получил 403, Content-Type application/json, 68 байт. Успешный стандартный набор включает Accept для XLSX, Accept-Language и Referer главной страницы. Он повторно получил 200 в новых сессиях, в том числе с прозрачным User-Agent **UpgradeLab/1.0**. Личный браузерный профиль, чужие cookies, CAPTCHA, обход IP-блокировки, TLS impersonation и отключение сертификатов не использовались.

**Конкретное серверное правило, вызвавшее 403, не установлено.** Проверялся набор стандартных заголовков, а не каждый заголовок по одному. Нельзя доказанно приписывать отказ одному User-Agent, отсутствию Laravel-cookie, CSRF, IP или антибот-системе. Подтверждён рабочий сценарий; серверных логов нет. Прогрев сессии и браузерный User-Agent для успеха оказались необязательны.

Регулярное расписание не включалось.

## 3. Загрузчик и безопасность

`SafeSession.get_to()` использует тот же HTTPS-транспорт, проверку DNS/IP, закрепление адреса, проверку сертификата, deadline и разрешённые редиректы. Ответ 200 передаётся порциями в файловый sink без накопления полного сетевого ответа в памяти. Wire-size и размер после HTTP-декомпрессии ограничены 8 MiB, включая gzip/deflate. Ответы ошибок не записываются в sink. Для остальных существующих HTTP-клиентов поведение get/post сохранено.

`fetch_official()` принимает только локальную директорию и опциональный внутренний transport для тестов; URL фиксирован, пользовательский URL не принимается. Заголовки стандартные и постоянные, User-Agent UpgradeLab/1.0. Никакого перебора заголовков/сессий в production. Сертификат проверяется. Допустимые домены редиректа только regard.ru/www.regard.ru.

Скачивание идёт в собственный `.part`, SHA-256 считается на потоке. Проверяются HTTP 200, точный XLSX MIME, ZIP-сигнатура, native-структура и CRC. Только после проверки файл атомарно заменяет `price.xlsx`; при ошибке удаляется только собственный partial, предыдущий файл не трогается. Sidecar содержит безопасные метрики, имя, хеш и native-статистику. Структурированные сообщения логов не содержат Cookie, Set-Cookie, токенов и приватных заголовков.

Максимум две попытки с паузой 0.25 с только при timeout/5xx. 401/402/403/404/429 немедленно останавливают загрузку. Повтор после 429 автоматически не запускается, ранний обход Retry-After не выполняется. Переключения IP/прокси/браузерного fingerprint нет.

Потоковой является **сетевая запись**. Существующий parser затем читает ограниченный сжатый XLSX и потоково обрабатывает XML; выбранные строки/план материализуются. Утверждение о полностью O(1)-памяти всего ETL было бы неверным.

## 5. Запуск и расписание

Из `backend`, для отдельной разовой диагностики, без обращения к БД:

```powershell
.\.venv\Scripts\python.exe -m scripts.diagnose_regard_download --output ..\.artifacts\regard-download-new --confirm-official-download
```

Папка обязана быть новой. Дополнительный `--warm-session` проверяет главную и собственную свежую сессию; для обычного скачивания не требуется. Секреты и пользовательские cookies не нужны.

Ежедневный привилегированный запуск использует существующий CLI:

```text
python -m scripts.regard_sync --database /data/pc_upgrade.db --schema /data/regard-schema.json --rights /data/regard-rights.json
```

Он не обходит существующие gates: REGARD_DOWNLOAD_ENABLED, точный REGARD_PRICE_URL, действительные automatic_download-права CatalogAccess и source_permissions. Реальный .env и production-права не менялись. Настройка доверия источнику сама по себе не публикует товары без разрешения/public eligibility.

Неактивный `tools/regard_daily.example.json`: `0 4 * * *`, UTC, то есть 07:00 по Москве. Один внешний исполнитель, не scheduler в FastAPI worker. Cron задаёт один плановый запуск в сутки, OS-lock исключает параллельные, hash/receipt защищают повтор. Последовательная ручная коррекция в тот же день допускается существующей бизнес-логикой.

**Готовность Amvera:** код и командная схема подготовлены, фактические scheduler, постоянный диск, сетевой доступ и права регулярного использования не подтверждены. Расписание не активировано, deployment не выполнялся. Локальный HTTP 200 не доказывает доступность из IP хостинга и не является разрешением магазина на регулярный импорт/публикацию.

Условие резервного браузерного admin-upload («сервер продолжает возвращать 403») не наступило: официальный download заработал. Новых административных HTTP API, ролей и веб-загрузки не добавлялось; их авторизация не выдаётся за проверенную. Ручной локальный импорт сохранён и проверен на настоящем новом файле. Если доступ впоследствии снова закроется, данные сохраняются, а не заменяются заглушкой; отдельный браузерный административный workflow потребует реализации в следующей согласованной задаче.
