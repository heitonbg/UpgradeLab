## Реализация и границы доверия

`RegardFeedAdapter` в `app/services/regard_feed.py` читает OpenXML потоково; структура, дата и заголовки проверяются, категории отслеживаются по уровням. Reader подключён через `CatalogSchema.input_adapter=regard-native-v1` к существующим prepare_import/apply_import. Плоский CSV/XLSX reader сохраняет прежние лимиты.

Для native XLSX отдельные границы: 8 MiB compressed, 64 MiB expanded archive, 48 MiB отдельный XML, 100 000 строк, 250 000 shared strings, восемь колонок. Запрещены path traversal, дубли ZIP entries/выбранных ID, DTD/entities, формулы, macros/ActiveX/external-workbook content. Архив не распаковывается в файловую систему. В ORM загружаются Hardware и выбранные категории, не все 83 тысячи товаров.

PN с пробелами/скобками хранится как исходный артикул, когда стабильная идентичность уже задана numeric external_product_id. Идентификатор проверяется отдельно. Идентичность по-прежнему SHA(source + external_product_id), без второго справочника/механизма StoreOffer. Цены — Decimal, дробные суммы не округляются в integer RUB. Суффиксы и VRAM проверяются действующими нормализаторами.

В файле нет product URL и доказательства наличия. Их отсутствие сохраняется. Для отдельной `.analysis.db` разрешена локальная материализация 2 335 анализируемых StoreOffer, origin=catalog_import, availability=unknown. Это не публичные и не подтверждённые предложения. Их относительный internal reference содержит ID локального каталога и **не является URL карточки Регарда или ссылкой покупки**, slug не придуман. Массовых запросов за URL/фото не было.

Доступ к этим строкам даёт только Python-контекст `closed_catalog_analysis(engine)`, привязанный к точному пути отдельной SQLite с суффиксом `.analysis.db`. Обычный API, другой engine и fixture-контекст его не включают. Владелец CLI может использовать `--closed-analysis`; HTTP-параметра обхода нет. Public audience + analysis запрещены. CatalogAccess остаётся real/non-fixture, public_enabled=false, automatic_download=false. В публичном поиске — 0 результатов; в закрытом поиске RTX 5060 — 16. Сокеты во время демонстрации запрещены.

В CatalogImport receipt сохранены SHA исходного файла/схемы и version; CatalogObservation связан с receipt. StoreOffer содержит external_product_id, source_updated_at/imported_at, exact price, provenance и analysis_only. Новый прайс не создаёт price_verification/checked_at и не продлевает проверку карточки.

## Запуск и ежедневная обработка

Из backend, для нового каталога результата:

```powershell
.\.venv\Scripts\python.exe -m scripts.regard_feed --file ../.artifacts/regard-feeds/regard_price_091126_17.xlsx --output ../.artifacts/regard-analysis-new
```

Команда создаёт отдельную БД, копирует существующий справочник из seed_data.json, сохраняет schema/rights/preview/result, применяет транзакционно и проверяет повторную идемпотентность. Существующий каталог анализа не перезаписывается. Реальные данные **не** используют --fixture.

Сравнение двух локальных файлов:

```powershell
.\.venv\Scripts\python.exe -m scripts.regard_feed --file <new.xlsx> --compare-with <previous.xlsx>
```

Новый/изменённый/неизменённый товар, изменение цены и missing определяются по фиксированному source=regard + external_product_id. Изменение только даты не считается изменением товарных параметров; при этом новая дата наблюдения хранится отдельно. В наличии только один настоящий файл: переходы проверены на маленьких явно синтетических XLSX в тестах, вторая реальная ежедневная выгрузка не симулировалась.

Для следующей выгрузки в той же isolated DB используйте существующий scripts.import_catalog preview/apply со schema.json. Apply требует rights.json и --confirm-owner-rights; дополнительно --closed-analysis. По умолчанию сокращение выбранного ассортимента более чем на 30% останавливает транзакцию. --allow-shrink — явное решение оператора после preview. Отсутствующий товар получает missing_from_feed, скрывается в анализе, но его StoreOffer, CatalogProduct, цены истории и сохранения не удаляются. Ошибочная структура/цены/архив, stale plan или конфликт транзакции не затирают предыдущее состояние. Изменение старого файла требует нового preview; одинаковый файл идемпотентен.

`tools/regard_daily.example.json` — выключенное расписание 22:30 Asia/Krasnoyarsk. `tools/regard_daily_preview.ps1` берёт только локально предоставленный XLSX, считает SHA, создаёт preview через существующий CLI; нет скачивания, автоматического apply, публикации или регистрации задачи. Если Hardware/schema изменились, старый план нужно пересоздать вручную. Никакие параметры Amvera не предполагаются.

На этой машине: открытие ZIP 0.0006 с; native разбор 8.56 с; нормализация 0.60 с; полный preview 9.18 с; apply 14.35 с. Apply включает повторное чтение/проверку плана. Пиковый working set процесса 195.88 MiB (Windows GetProcessMemoryInfo, включая Python/ORM/планы; не размер файла и не гарантия production). Измерения окружения разработки, не SLA.

19 новых регрессионных тестов покрывают структуру, вложенные категории, несовпадающую дату/заголовок/ID, compare, price changes, чужой database context, public denial, неизменный импорт, missing/shrink и ошибки файла. Backend-зависимости и таблицы не добавлены; миграция рабочей БД не требовалась и не выполнялась.

Для публичного запуска нужны разрешения на отображение/автоматическое получение, подтверждённый часовой пояс/условия источника, реальные доказательства остатков/логистики, точные технические профили и нагрузочная проверка. Отсутствующие данные не заменены предположениями.

После обновления контракта CatalogSchema ранее подготовленные preview-планы нужно сформировать заново: проверка SHA схемы намеренно отклоняет устаревший план. Уже импортированные товары и история при этом не удаляются.
